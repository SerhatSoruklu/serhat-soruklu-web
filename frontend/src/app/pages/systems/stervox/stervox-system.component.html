C17 · LIBEVENT · LIBPQ · POSTGRESQL

An unusual stack.
A deliberate choice.

VOXCORE takes a C-first approach: explicit control over memory, resources and failure paths. C17 is the stable baseline; libevent supports event-driven networking, and libpq connects the core to PostgreSQL, the chosen home for durable state.

The aim is a small, understandable core with predictable decisions and fewer hidden runtime behaviours. C gives us direct control without a garbage-collected backend runtime; memory safety, bounded work and recovery become deliberate engineering responsibilities.

TypeScript handles the web experience. The architecture keeps pure decisions separate from external effects, so the same inputs can be checked against the same rules. Reliability is earned through evidence, not a language choice.

FOR THE CURIOUS · INSIDE VOXCORE

Trust should leave evidence.

The foundations use C and TypeScript, with PostgreSQL selected for durable state. Here is what the source already shows, and what the financial-core design is working towards.

01 Money counted precisely In code

£100 becomes 10,000 pence, stored as a whole number with its currency. The C money primitive checks for overflow and rejects addition across different currencies. The web money type uses bigint. 

export interface Money {
  minor: bigint;
  currency: string;
  exponent: number;
}

Source: client/src/core/money.ts, server/src/core/money.c and server/tests/test_money.c. These are money primitives, not a live banking ledger.

02 A history you correct, never quietly erase Ledger design

The ledger specification proposes balanced double-entry records. Each journal must balance within its currency: money cannot simply appear because a screen says it should. Corrections are new, linked entries that preserve the original history. 

sum(postings_in_one_currency) == 0
correction → linked compensating entry

Illustrative design, not running ledger code. Source: VOXCORE Ledger Master v0.1, corrected R1 edition, accounting invariants and journal lifecycle. The production ledger remains to be implemented.

03 A retry must not become a second charge Deduplication design

A timeout is uncertainty, not permission to move money again. The planned approach uses operation keys and request fingerprints to recognise retries, reject conflicting reuse and reconcile uncertain external results before attempting another effect. 

same key + same request → original outcome
same key + changed request → conflict
unknown external outcome → reconcile first

Source: VOXCORE Ledger Master v0.1, idempotency and concurrency; STERVOX 2036 Master Execution Map, VOXCORE architecture. These safeguards are requirements, not deployed guarantees.

04 Own the customer-checking decisions KYC design

KYC means checking who a customer is. Stervox’s design separates evidence from specialist providers, policy assessments and human decisions. A provider’s “pass” is evidence to review, rather than automatic permission for every product.

The aim is a decision trail that can explain which evidence, policy version and authority applied at the time.

Source: server/src/modules/onboarding/kyc/README.md. This module is a design scaffold; customer due diligence and production verification are not implemented.

A TEN-YEAR HORIZON · 2026–2036

Earn the next phase.

The launch target is 5 January 2027. The sequence below summarises the direction; each release depends on evidence, operating readiness and the permissions and partnerships its scope requires.

  1. NOW

    Build the foundations

    Product experience, money primitives, architecture and controlled test slices. This is the current development stage.

  2. PLANNED LAUNCH

    Start with financial clarity

    An initial UK direction around account information, rewards and opt-in credit insights. Confirm the available scope through release gates.

  3. AFTER VALIDATION

    Prove reliability, then expand

    Validate connections, reconciliation, recovery and customer usefulness before widening coverage or product scope.

  4. LATER · CONDITIONAL

    Accounts, cards and a broader platform

    Partner accounts and cards belong to later product Phase 6. Each needs separate commercial, financial and operational acceptance.
